# shufflesync — Spotify playlists → iPod shuffle (2nd gen)

**Date:** 2026-06-01
**Status:** Approved design

## Summary

A one-command macOS CLI that takes a Spotify playlist URL, downloads matching
audio via `spotdl`, and mirrors it onto a 2nd-generation iPod shuffle by writing
the device's native `iTunesSD` database directly — no iTunes required.

```
shufflesync <playlist-url>
```

## Goals

- Get a Spotify playlist's tracks onto a 2nd-gen iPod shuffle in a single command.
- Be iTunes-free for the sync step.
- Reliable downloads by reusing the well-solved `spotdl` matching pipeline.
- Fill the genuine tooling gap: writing the shuffle's `iTunesSD` database.

## Non-Goals (YAGNI)

- Other iPod models (nano uses the very different `iTunesDB` format). Shuffle 2nd
  gen only.
- Other shuffle generations (1st gen differs; 4th gen needs a checksum/hash).
- Initializing a blank/unformatted device. We assume the shuffle has already been
  set up by iTunes at least once and therefore has an `iPod_Control/` folder.
- "Add to existing" sync. We do mirror (replace-all) only.
- Two-step download/sync split, TUI, or GUI.
- Extracting Spotify's own DRM-protected audio (not technically possible; `spotdl`
  matches tracks from YouTube and tags them with Spotify metadata).

## Constraints / Assumptions

- macOS host. Shuffle mounts under `/Volumes/`.
- Shuffle is FAT32 and already iPod-formatted (`iPod_Control/` present).
- Output audio is MP3 (compatible with 2nd-gen shuffle).
- Requires `spotdl`, `yt-dlp`, and `ffmpeg` on the host.
- Public Spotify playlists (spotdl ships with working API credentials, so no user
  auth/setup is required).

## Architecture

Three components with clear boundaries.

### 1. Downloader (`downloader.py`)

Thin wrapper around `spotdl`.

- **Input:** Spotify playlist URL + a cache directory.
- **Behavior:** invokes `spotdl` to fetch/match/tag tracks as MP3 into
  `~/.shufflesync/cache/<playlist-id>/`. Preserves playlist order. Caches
  downloads so re-syncing an unchanged playlist does not re-download.
- **Output:** an ordered list of local MP3 file paths.
- **Depends on:** `spotdl`, `yt-dlp`, `ffmpeg`. Presence is checked at startup
  with actionable install hints if missing.

### 2. Device manager (`device.py`)

Finds and exposes the mounted shuffle.

- Scans `/Volumes/*` for a mount containing an `iPod_Control/` folder.
- 0 found → clear, actionable error. 2+ found → prompt the user to pick.
- Exposes the device root and the `iPod_Control/Music/` target directory.
- **Depends on:** filesystem only.

### 3. Sync engine (`sync.py` + `itunessd.py`)

The actually-missing piece. Mirror semantics.

- Wipes `iPod_Control/Music/`.
- Copies the playlist's MP3s in, with sanitized short ASCII filenames.
- Writes a fresh `iTunesSD`, then flushes to disk.
- `itunessd.py` is a focused, standalone module that serializes the 2nd-gen
  `iTunesSD` binary format: a header (track count + fixed constants) followed by
  one fixed-length record per track containing playback flags and the track's
  file path stored as fixed-width UTF-16, in the device-relative path format the
  shuffle expects.
- **Depends on:** the device manager's paths and the downloader's ordered file
  list.

## Data Flow

```
playlist URL → Downloader → [ordered MP3 paths]
                                   ↓
              Device manager → [device root, Music dir]
                                   ↓
   Sync engine: wipe Music → copy files → write iTunesSD → flush
```

## The `iTunesSD` Format (primary technical risk)

The 2nd-gen `iTunesSD` is a documented binary format described in the
iPodLinux / libgpod references, with proven reference implementations
(libgpod's `itdb_shuffle_write`, the older `shuffle-db` script).

De-risking strategy — do not trust memorized byte offsets:

1. Implement `itunessd.py` from those references.
2. **Validate against ground truth.** Use a real `iTunesSD` generated by iTunes
   (or a reference tool) for a known set of files as a golden fixture. A test
   asserts our serializer reproduces the same bytes for the same input. This
   converts "are the offsets right?" into a concrete pass/fail.

If we can copy an existing iTunes-generated `iTunesSD` off the device, that
becomes the golden fixture. Otherwise we build to spec and verify empirically by
playing the result on the device.

## Capacity Handling

A 2nd-gen shuffle holds ~1–2 GB; playlists can exceed that. Under mirror mode:
sum file sizes, and if the playlist won't fit, **fill in playlist order up to
capacity and warn** which tracks were skipped (do not abort).

## Error Handling

- Missing `spotdl` / `yt-dlp` / `ffmpeg` → startup check with install hints.
- No shuffle mounted → clear error naming what to plug in.
- Multiple candidate devices → interactive pick.
- A track `spotdl` cannot match → reported in a summary; sync continues with the
  rest.
- Capacity overflow → warn + skip overflow tracks (see above).

## Testing Plan

Built test-first (TDD).

- `itunessd.py`: golden-bytes test against an iTunes-generated `iTunesSD`; unit
  tests for edge cases (0 tracks, unicode titles, long filenames).
- Device manager: tested against a temp dir faked to look like a mounted shuffle
  (contains `iPod_Control/`); covers the 0 / 1 / many-device cases.
- Downloader & sync: tested with `spotdl` mocked and a fake device dir, asserting
  files land in `Music/` and the database matches the ordered file list.
- Real end-to-end run on the actual device for final verification.

## Runtime / Packaging

Python 3 (matches `spotdl`). Packaged so `shufflesync` is a single installable
console command.
